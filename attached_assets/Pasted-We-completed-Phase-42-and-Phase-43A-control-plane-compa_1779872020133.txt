PHASE 43B — Real Grader Support for json_equal

Goal:
Turn json_equal from contract-shaped validation into real server-enforced validation where safe.

Why:
Phase 42 showed that most visible-project validation is contract-shaped. json_equal is the best first real-grader target because it is common, deterministic, safer than SQL execution, and does not require external services.

10. Identify what should happen when expected JSON is malformed.

Preferred implementation:
Small, deterministic json_equal support in the existing grading helper.

Behavior:
- Parse learner submission as JSON.
- Parse expected JSON from validation spec or expectedOutputs, according to existing content shape.
- Compare structurally, not string-wise.
- Ignore object key order.
- Preserve array order unless existing spec clearly says otherwise.
- Return clear failure messages without leaking full answer.
- Do not execute code.
- Do not call external services.
- Do not alter /submit integrity semantics.
- Do not change XP/completion evidence behavior except that json_equal can now fail honestly.

If existing json_equal specs are inconsistent:
- Stop and report the compatibility problem.
- Prefer a conservative implementation plus audit warnings over breaking many projects.

Testing:
Add focused tests for:
1. exact structural match passes.
2. object key order differences pass.
3. array order differences fail unless explicitly allowed.
4. invalid learner JSON fails cleanly.
5. malformed expected JSON fails safely.
6. extra fields behavior is explicit and tested.
7. missing fields fail.
8. no answer leakage in failure message.
9. existing exact/contains/regex behavior remains unchanged.
10. /check or route-level test if current harness supports it.

Audit update:
Update validationEnforcement classifier/matrix so json_equal moves from contract-shaped to enforced only if implementation is complete and tests pass.
