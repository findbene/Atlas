PHASE 42 — Validation Kind Reality Check + Authoring Guardrail

Goal:
Make Atlas’s validation-kind story explicit, honest, and mechanically guarded before scaling new project production.

Why:
Atlas’s credibility depends on project validation. Some validation kinds are fully enforced by the current grader, while others appear to be contract-shaped metadata that the current grader does not actually execute. Before adding many more projects, we need a precise map and guardrail.

Read first:
1. HANDOFF.md
2. replit.md
3. docs/phases/INDEX.md
4. docs/phases/phase-41-seed-factory-pilot.md
5. docs/project-authoring-spec.md
6. scripts/src/audit-project-authoring.ts
7. lib/grading.ts or current grading implementation
8. validation-related schemas/types
9. existing authored projects using validation kinds
10. current /check and /submit route behavior

Start with a read-only audit.

Audit:
1. List every validation kind used by visible authored projects.
2. Count projects/steps per validation kind.
3. Identify which validation kinds are actually enforced by the current grader.
4. Identify which validation kinds are contract-shaped only.
5. Identify which kinds silently pass, partially pass, or fall through.
6. Identify which kinds are safe as metadata if clearly documented.
7. Identify which kinds are misleading for learner-facing validation.
8. Identify the smallest useful guardrail before scaling content.
9. Identify which real grader implementation would have the highest leverage later.

Preferred Phase 42 implementation:
Do not implement a large validation engine yet.

Implement a schema-free authoring/audit guardrail first.

Deliverables:

Create documentation, for example:
docs/validation-kind-matrix.md

- validation kind

B. Audit Guardrail
Update audit:authoring or add a companion audit so validation kinds are no longer ambiguous.

The audit should:
- report contract-shaped validation kinds explicitly
- distinguish “publish-ready under current contract” from “machine-enforced by grader”
- avoid breaking the current 58/58 unless we intentionally choose to fail contract-shaped validations
- preferably emit warnings/metadata first, not hard failures
- make the convention explicit so future project authors cannot misunderstand it
